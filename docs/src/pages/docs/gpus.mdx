## Worker model

`--gpus W` creates up to W workers, and never more workers than the plan has
work units. Under the unit partition several GPUs can share a reference bin,
each running its own slice of the bin's query units and building its own copy
of the bin, so GPUs beyond the reference-bin count are used (0.1.0; hg38 has
seven bins, and the eighth A100 used to idle). Under whole-bin ownership, and
with `HSPZ_WORKER_CAP=bins`, a run starts at most one worker per reference bin. When each worker has its own device and every device the run uses
is the same class (equal SM count and L2, nominal clocks within 10%), the frozen
plan's work units are split across the workers by estimated cost. Each unit is
weighted by its reference bin's length times its query bin's length; whole
reference bins go to the least-loaded worker while they fit within its share,
and the remaining bins form one stream of query slices, cut so that the busiest
worker carries as little as possible, at the price of at most one extra
reference build per extra worker. This cost split is used only when it models at
least 3% lighter than the count quotas of 0.0.4 (whole bins first, then
contiguous query slices of equal unit counts); otherwise those count quotas run
unchanged. Units of very different sizes, such as 1.7 Gbp axolotl chromosomes
next to small scaffolds, are where count quotas fail: on two A100s an
8-record axolotl query against xenTro9 fell from 1,469 s to 1,107 s
(−24.7%). Otherwise each worker owns complete reference bins, assigned by
deterministic longest-processing-time scheduling, and runs every query bin
against them. `HSPZ_UNIT_PARTITION=0|1` forces either policy and
`HSPZ_UNIT_COST` chooses the weights (see the knobs below). More workers than
devices time-slice a device and are a correctness configuration, not a speed
configuration.

Every GPU run prints `schedule:` lines with the chosen policy, the reason for it and
each worker's visits, written `R<bin>[<first>..<end>)` for a reference bin and
its slice of query bins. With `--time`, one `unit ledger:` row per work unit
adds its worker, device, bins, GPU time, host start and end, seeds, hits and
HSPs, followed by each worker's finish and busy times.

GPU completion order never controls output order. Each result carries its
`WorkUnit.ordinal`, and the emitter replays those ordinals in the planned order.
A duplicate or out-of-plan work unit is an error, and once the workers have
finished the emitter checks that every unit arrived.

## Seeder policy

| workers | default query seeder |
| ---: | --- |
| 1 | CPU: up to six producer threads run ahead of the GPU, with pinned asynchronous upload when supported |
| more than 1 | device |

For controlled measurements only:

```bash
HSPZ_DEVICE_SEEDS=0 hspZ run ...  # force CPU
HSPZ_DEVICE_SEEDS=1 hspZ run ...  # force device
```

## Runtime tuning knobs (0.0.5)

Every knob is exact: every mode produces the same HSP set and the same bytes.
An unrecognised value of `HSPZ_REF_BUCKETS`, `HSPZ_REF_BUCKET_SHIFT`,
`HSPZ_UNIT_PARTITION`, `HSPZ_UNIT_COST`, `HSPZ_WORKER_CAP`, `HSPZ_SEED_PRODUCERS` or
`HSPZ_QUERY_PACK_AHEAD` is an error; `HSPZ_CHUNK_WALK` and
`HSPZ_DEVICE_SEEDS` ignore values they do not know, and a non-integer
`HSPZ_FIND_HITS_WARP_MIN_DENSITY` or an unknown `HSPZ_GATE_SIEVE`,
`HSPZ_SIEVE_WORDS`, `HSPZ_GATE_SIEVE_MASK`, `HSPZ_FIND_HITS_GROUPS`, `HSPZ_HITS_BUCKETED`, `HSPZ_BUCKET_VOTES`,
`HSPZ_SURVIVOR_ORDER` or `HSPZ_SEED_TABLE` is ignored with a
warning.

| variable | default | what it does |
| --- | --- | --- |
| `HSPZ_GATE_SIEVE=1\|0\|gather\|auto` | `1` | The score-gate sieve (0.1.0): each lane bounds its own anchor from 2-bit packed bases and only the anchors it cannot reject are scored exactly. `0` scores every anchor exactly, as 0.0.6 did. `gather` loads the bound's reference words through shared memory instead of once per lane, which is faster where memory bandwidth binds (L4 without its bucket pass: 30.5 s against 41.0 s for unit 0 of hg38 × mm39) and slower where it does not (A100: 19.0 s against 16.0 s); `auto` gathers only when the bucket pass is off. `--time` prints `gate sieve: on` with the class scores, or `off` with the reason. |
| `HSPZ_SIEVE_WORDS=R,L` | `4,5` | How far the sieve carries a side of its bound that has not decided, in 32-base words: every lane reads 2 words to the right and 3 to the left, and an undecided side walks on up to `R` (2 to 4) and `L` (3 to 5). `2,3` is the first window alone, which sent 1.4% of human–mouse anchors to the exact scorer; the default leaves 0.02% (hg38 × mm39 on an A100: 656 → 588 s). |
| `HSPZ_GATE_SIEVE_MASK=0\|1` | `0` | Whether the sieve's bound reads a mask plane of the query (0.1.0). `0`: a query base that is not an uppercase A, C, G or T is packed as G and bounded by the class scores, and no mask plane is built (hg38 × mm39 on an A100: the gate 244 → 217 s, whole genome −5.4% and −5.9%, eight cards −6.5%). `1`: the bound stops at such a base, which then has to end an extension, so the sieve is off at `--xdrop` 1000 or above and with IUPAC codes other than N in the query. `HSPZ_GATE_SIEVE=gather` and `auto` always keep the plane. Both give the same output. |
| `HSPZ_GATE_SIEVE_GUARD=<n>` | 32 | Every n-th score-gate launch counts the anchors the sieve passed; if that is more than half of them, the launches up to the next count run the exact gate alone, so regions where the sieve rejects little (long unmasked satellite arrays) do not pay for both. `0` removes the guard. A run where it acted prints a `#sieve guard:` line. |
| `HSPZ_GATE_SIEVE_COUNT=1`, `HSPZ_GATE_SIEVE_CHECK=1` | unset | Diagnostics, never for a timed run: both wait on every batch. `COUNT` prints how many anchors the sieve passed to the exact scorer. `CHECK` also recomputes every anchor on the host, the lane's decision and the exact score gate, and reports any disagreement with the device (`assets/tests/sieve-identity.sh`). |
| `HSPZ_REF_BUCKETS=auto\|1\|0` | unset | Reference-locality bucketing before the score gate. **With the sieve on (0.1.0) and the variable unset, the pass is on whenever a window sized for the sieve's packed planes fits half of the L2** (64 Mbp windows on an A100 or an L4), with no trial: on an A100 it takes unit 0 of hg38 × mm39 from 16.3 to 12.9 s of GPU time and the whole genome from 924 to 773 s. A chunk the sieve does not gate skips the pass. `0` turns it off and `auto` runs the trial described next, which is also what an unset variable does when the sieve is off. It wins where lower DRAM traffic lets a power-capped GPU raise its clock (L4: −6.5% whole-genome wall) and loses where the card already runs near its boost clock (RTX 4090: +3.7%). `auto` measures both paths per engine in blocks of ≥3 s, discards each block's first second, and after six blocks keeps bucketing only if it was at least 3% faster (median of the three off/on pairs) — about 20 s of gate time per engine. Shorter engines, for example 5 Mbp queries run as separate processes, stay on the off path, so set `HSPZ_REF_BUCKETS=1` on L4-class cards for those. `--time` prints the blocks and the decision. Cards whose L2 cannot hold the smallest window (T4) stay off. |
| `HSPZ_REF_BUCKET_SHIFT=<16..31>` | derived from L2 | Pins the bucket window to 2^shift bytes and turns bucketing on (`HSPZ_REF_BUCKETS=0` still wins). A shift that would need more than 32 buckets for a reference bin is an error. |
| `HSPZ_HITS_BUCKETED=1\|0\|check[:N]` | `1` | How a bucketed batch's anchors get into bucket order (0.1.0). `1`: written there directly from the seeds, from each k-mer's hits per window (4 bytes per k-mer on the device, plus rows of window edges for the k-mers with more than 14 hits in a window); no anchor is written in seed order, counted or scattered (hg38 × mm39 on an A100: expansion and bucketing 180 → 100 s of GPU, whole genome −15.7% and −16.2%, eight cards −14.9%). `0`: expanded in seed order, counted and scattered, as before; also what `--paired`, `HSPZ_FIND_HITS_GROUPS=0`, `HSPZ_SURVIVOR_ORDER=raw`, more than eight windows, a seed of more than 12 care bases and the diagnostics that show an order use. `check`, or `check:N` for the first N batches, runs both and compares each window's anchors on the host (a diagnostic, never for a timed run). The output is the same. |
| `HSPZ_FOLD=1\|0\|check` | `1` | The transition fold (0.1.1): a reference bin gets a second seed table, built on the device, in which every k-mer also holds the positions of its single-transition variants, and the query is seeded once per position instead of 13 times. The hits of a batch are the same (hg38 × mm39 on one A100: 376.2 → 334.5 s without `--time`). It takes 13 times the position table in device memory (8 to 10 GiB for a bin of hg38) and is built only where `--max-hits` still fits beside it; a batch of `--max-hits` hits or more is run on the plain tables, and the fold is dropped for a reference when a chunk needs its memory or more than a quarter of the batches are such batches. Off with `--notransition`, `--paired`, `--dump-raw`, `--hit-stats`, seeds of more than 12 care bases and wherever `HSPZ_HITS_BUCKETED` is not in effect; `--time` prints what was built or why not. `0` switches it off. `check` compares every device-built table with one built on the host and stops at the first difference (a diagnostic). |
| `HSPZ_FOLD_RUN=<1\|2\|4\|8\|16\|32>` | `4` | Folded seeds per warp of the kernels that write a batch's anchors in window order (0.1.1). A folded seed has 13 times the hits of a plain one; on an A100 unit 0's writer takes 2,026 ms with 32, 1,313 ms with 4 and 1,653 ms with 1. For controlled measurements. |
| `HSPZ_FOLD_COUNT=1\|0` | `1` | How a folded batch is counted (0.1.2). `1`: the fold's build also records every k-mer's hits per reference window beside its table, and one kernel sums them for each run of four seeds and window, in the layout the anchor writer reads; the batch's hit total is the scan of those sums, saturated so that a batch past 2^32 hits is still seen as too large (unit 0 on an A100: the counts take 124 ms of GPU instead of 215; hg38 × mm39 on one card 326.2 → 322.2 s without `--time`). `0`: the three kernels of 0.1.1, a count per seed, its scan and the counts per run and window. The anchors are the same. |
| `HSPZ_BUCKET_VOTES=match\|loop` | `match` | How the two kernels of the bucket pass learn which lanes of a warp share a bucket (0.1.0). `match`: one match instruction per warp (hg38 × mm39 on an A100: the pass 147 → 127 s of GPU, whole genome −3.5%, eight cards −3.2%). `loop`: one vote per bucket, as before. Both write the same buffers. |
| `HSPZ_SURVIVOR_ORDER=slots\|raw` | `slots` | In which order a bucketed batch's survivors reach the extension (0.1.0). `slots`: in bucket order, straight from the kept bits; the bucket pass writes no raw ids and nothing is sorted (hg38 × mm39 on an A100: whole genome −5.2% and −5.3%, eight cards −3.3%). `raw`: mapped back to the order of before the pass and sorted, as before. The output is the same: the host sorts every batch's HSPs. `--dump-raw`, the census and `HSPZ_BUCKET_ORDER_CHECK` use `raw`. |
| `HSPZ_BUCKET_ORDER_CHECK=<n>` | unset | Diagnostic, never for a timed run: for the first n batches the anchors and raw ids the bucket pass wrote are copied to the host and checked to be the stable permutation by bucket, and the restored survivor order to be ascending. A violation prints a `#bucket-check-violation` line. |
| `HSPZ_CHUNK_WALK=full` | sparse | Restores the pre-0.0.4 chunk walk that copied the whole cumulative hit array for every seed batch above `--max-hits` (rollback only). |
| `HSPZ_UNIT_PARTITION=0\|1` | unset (auto) | Splits the frozen plan's work units across workers (weighted as `HSPZ_UNIT_COST` says) when every device the run uses is the same class and each worker has its own device (W=1, time-sliced workers and mixed classes keep whole-bin ownership); output is unchanged. `0` forces whole-bin ownership and `1` forces the partition; any other value, including `auto`, is an error. With the 0.0.4 count quotas: −11.9% seed-and-filter wall on 2× RTX 4090 (1,400 → 1,233 s) and −5.1% on 4× RTX 4090 (718 → 681 s) at `MAX_HITS=16,711,680`. Other worker counts and device classes are unmeasured; compare with `HSPZ_UNIT_PARTITION=0`. |
| `HSPZ_UNIT_COST=bp\|count\|hits:PATH` | `bp` | How the partition weighs work units. `bp` (reference bin bp × query bin bp, from the plan alone) uses the cost split when it models at least 3% lighter than the count quotas; `count` restores the 0.0.4 count quotas exactly; `hits:PATH` weighs units by a `hspZ hits-estimate` table of this exact plan (its seed hits plus 6 per query bp, 1% margin; a table for another plan is an error, and batch mode rejects it). The `note: unit cost …` line reports both modelled splits and the choice. On two A100 80GB: an axolotl query of 4 chromosomes + 4 scaffolds against xenTro9 (3×8 units) 1,469 → 1,107 s (−24.7%), HLmyoMyo6 × HLmyoDau2 at 50% (3×3) 482 → 400 s (−17.1%); a balanced plan (danRer11 × oryLat2, 3×2) keeps the count split. |
| `HSPZ_WORKER_CAP=units\|bins` | `units` | How many workers a run may start. `units` allows up to one per work unit when the unit partition is in use (whole-bin ownership keeps one per bin and says so), so GPUs beyond the reference-bin count are not idle: hg38 × mm39 on eight A100s, 136.9 → 126.2 s. Each extra worker on a bin builds its own copy of the bin and needs its own host memory for it. `bins` restores at most one worker per reference bin (the default before 0.1.0). |
| `HSPZ_SEED_TABLE=partitioned\|rounds\|two-pass` | `partitioned` | How a reference bin's seed table is built on the host (0.1.0). `partitioned`: positions go to the stream of their k-mer's leading bases and each partition is sorted inside a cache; a bin's pairs (8 bytes per position) are held at once where the host budget allows, in rounds otherwise (hg38 × mm39 on eight A100s: 7–9 s → 1 s per worker, 100 → 91 s). `rounds`: always in rounds of at most max(512 MiB, the old builder's count tables). `two-pass`: the builder of 0.0.x. The tables are byte-identical. |
| `HSPZ_FIND_HITS_WARP_MIN_DENSITY=<n>` | 8 | Mean hits per seed from which a `find_hits` launch walks each seed with one warp instead of one thread (16 before 0.0.5; `0` sends every launch to the warp kernel). Only used with `HSPZ_FIND_HITS_GROUPS=0` and by `--paired` since 0.1.0. For controlled measurements; see [the algorithm notes](/hspZ/docs/algorithm/hit-discovery/). |
| `HSPZ_FIND_HITS_GROUPS=1\|0\|check` | `1` | Which kernel expands seeds into anchors (0.1.0). `1`: one warp per run of 32 consecutive seeds, four rounds of positions in flight (hg38 × mm39 on an A100: `find_hits` 135 → 73 s, whole genome −7.8%). `0`: one thread or one warp per seed, as before. `check` runs both on every chunk, compares every anchor on the host and stops at the first difference (a diagnostic, never for a timed run). |
| `HSPZ_SEED_PRODUCERS=<0..64>` | unset | Host seed generation at one worker (0.1.0). Unset: one single-threaded producer per CPU thread, at most six and at most 512 MiB of seed slots, running ahead of the GPU. `0`: one batch at a time split over all threads, as before 0.1.0. `1..64` pins the number of producers. |
| `HSPZ_QUERY_PACK_AHEAD=1\|0` | `1` | Packs the next work unit's query bin on a thread while the current unit runs (0.1.0), if the host budget has room for one more packed bin per worker beside reference prefetch. `0` packs each bin when its unit starts. |
| `HSPZ_QUERY_PACK_CACHE=1\|0` | `1` | Keeps every packed query bin to the end of the run (0.1.2), so a bin is packed once instead of once per reference visit. On only with `HSPZ_QUERY_PACK_AHEAD` and where the host budget has room for all of the run's query bins at once beside everything else it counts (hg38 × mm39 on one A100: packing 5.3 → 0.8 s of host time, 327.0 → 322.5 s without `--time`, peak RSS 11.5 → 20.0 GB). `0`: each unit packs its bin, as in 0.1.1. |
| `HSPZ_LEAN_BATCHES=1\|0` | `1` | Where the host does its work between two batches (0.1.1). `1`: the next seed batch's upload is issued, and the previous batch's HSPs are sorted and deduplicated, inside the current batch while its kernels are queued (hg38 × mm39 on one A100: 381.8 → 376.5 s without `--time`). `0`: between batches, as in 0.1.0. The output is the same; `--dump-raw` keeps the sort inside its batch. |
| `HSPZ_TAIL=1\|0` | `1` | How a chunk's accepted HSPs are gathered (0.1.2). `1`: the extension is launched with one warp per survivor, up to its usual grid, and a chunk of at most 4,096 survivors has the survivors' records copied to the host, which keeps those with a positive score in their order, instead of scanning the finished flags, adding block offsets and compacting on the device (hg38 × mm39: 136,908 of 148,430 chunks; on one A100 325.0 → 322.2 s without `--time`). With `--hspthresh` below 2 every chunk takes the device path. `0`: as in 0.1.1. The output is the same. |
| `HSPZ_HOST_TRACE=1` | unset | Prints one `host trace:` line at the end of a run (0.1.1): the number of batch calls, the time the host spent inside them, and how much of it was waiting for the card, host work while kernels were queued, and host work with nothing queued, summed over the workers. It works without `--time`, whose own events are host work between kernels (6% of a one-card genome). A diagnostic. |

## Many queries against one reference

`--query-list` runs every listed query FASTA in one process:

```bash
hspZ run \
  --reference ref.2bit \
  --query-list queries.txt \
  --output OUT \
  --gpus 1
```

`queries.txt` holds one query path per line (blank lines and `#` comments are
ignored; relative paths are resolved against the directory of `queries.txt`).
Each reference bin is built and uploaded once instead of once per query, while
every query keeps its own plan, cap, seed batches, dedup scopes and `-D`
history, so its output under `OUT/000001/`, `OUT/000002/`, … is byte-identical
to a standalone run. `-Z` writes one archive per job (`OUT/000001.tar.gz`, …; a
path given to `-Z` is ignored with a note), and `--dump-plan`, `--dump-manifest`
and `--dump-raw` write one file per job with the job number appended
(`plan.tsv.000001`, …). `OUT/queries.tsv` maps job → path, size, sha256, blocks,
units, HSPs and completion. A failing job aborts the batch (partial outputs may
remain). `--query-list` belongs to `run`; `benchmark` and `--cpu-only` reject
it.

With `--gpus W` above one, the whole batch's work units are spread over the
workers by the same partition a single query uses (`HSPZ_UNIT_PARTITION` still
decides the policy, and the default `bp` weights apply; `hits:PATH` is for
single queries), and the receiver reorders each job's results, so the per-job
output is unchanged. On two RTX 4090s, 100 queries of 5 Mbp against hg38
finish in 255 s at `--gpus 2` against 497 s at `--gpus 1`; on one L4 the same
list takes 1,890–1,900 s batched against 10,400–11,600 s as separate runs. Both
arms of each comparison ran the same pinned settings (device seeder; bucketing on
for the L4, off for the RTX 4090s; the partition forced at `--gpus 2`), not the
`--gpus 1` defaults. Whole-chromosome queries (61–121 Mbp) gained 2.6%;
whole-genome queries are expected to gain under 1% (reference setup is 0.27% of
a whole-genome run; not measured in batch mode). The saving is the reference
preparation, which by the cost model dominates only below roughly 130 Mbp of
query per run on a 4090 (30 Mbp on an L4).

All jobs must plan to identical reference bins; `-B 0`, `--kegalign-bins` and
`--from-manifest` are rejected in batch mode, and a job whose standalone plan the
multi-worker device budget would change is refused rather than replanned.
Bin-major order delays the first result, so amortized time per query is not
request latency. Job directories (or archives) are created at the start (with
`--index`, when a job's first unit is written) and fill as units finish;
`OUT/queries.tsv` is written only after every job has succeeded, so in a fresh
`OUT` its presence marks a complete batch; a rerun into the same `OUT` does not
remove an earlier `queries.tsv`.

## Reusing a reference across runs

When queries arrive in separate runs, build the reference's tables once:

```bash
hspZ index --reference ref.2bit --index /local/ref.hspz-index
hspZ run --query q.fa --index /local/ref.hspz-index --output OUT
```

`hspZ index` writes each reference bin's seed tables and encoded bases as raw
arrays with a text manifest, published atomically once a `READY` marker is
written: the directory holds `MANIFEST`, `READY` and one subdirectory per bin
(`000`, `001`, …) with little-endian `index_table`, `pos_table` and `enc` files
without headers. It is built in a sibling `.tmp` directory and renamed onto the
`--index` path, which must not exist yet. A run given `--index` plans from the
reference record names and lengths stored in the `MANIFEST` and loads the arrays
instead of rebuilding, inside the same prefetch; its output is byte-identical
to a run without the index. Before any upload the run proves the index
matches: `--seed`, `--step`, `-B` and `--kegalign-bins` must equal the values it
was built with, and the resolved plan must have exactly the index's bins. Each
bin's arrays are then checked against their recorded lengths and checksums as
the bin loads, so a damaged file never reaches the device.

`--reference` is optional with `--index`. When it is given, the FASTA is
verified against the index in the background while the run proceeds: its
records must hash to the value recorded at index time (an edit of the same size
is caught) and carry exactly the index's record names and lengths. No output is
written until it matches; a mismatch exits non-zero and leaves no output files.
Without `--reference` no FASTA is read and the index is trusted; its arrays are
still checksum-verified as bins load. The run prints an `index: using …` line
before the workers start and an `index: loaded …` line with what it validated at
the end; with `--time`, the `lifecycle:` line adds a `loads` count, and a run
given `--reference` reports the background parse as
`input.reference (background)` and time the run spends blocked on the
verification as `index.verify wait` (plus the overlapped
`index.verify wait (emitter)`, the wait at a job's first unit).

hg38 at the default layout takes about 120 s to index and 8.9 GB on disk, and
each run then loads its seven bins in roughly 12 s. On an L4 all but the first
load (about 1.7 s) hide behind the GPU; on faster cards a small query's GPU time
per bin (about 0.6 s for 5 Mbp on an RTX 4090) is shorter than a bin load (about
1.8 s), so the loads set the pace. On an L4, with bucketing pinned on, the device
seeder and the index on local NVMe with a warm page cache, 100 queries of 5 Mbp
run as separate processes fall from 10,800 s to 2,680 s; those runs also
re-read and re-hashed the reference before planning (about 4–5 s for hg38). A
run without `--reference` skips that work entirely. On an L4 at the default
settings, separate 5 Mbp runs against an hg38 index (20 runs per arm, identical
output) took 23.5 s each without `--reference`, against 27.8 s when the
reference was parsed before planning (−15.6%); the first work unit started after
1.76 s instead of 6.15 s, and peak RSS fell from 5.1 GB to 2.0 GB. On an RTX
4090 (one pass per arm) the same runs took 16.0 s with `--reference` checked in the background and
15.8 s without it, against 20.8 s (−22.9% and −23.8%).
Keep the index on local storage: a bin load above 10 s warns, and on a slow
network file system loading can cost more than rebuilding. `-B 0` is rejected by
both commands, and a plan the device budget would shrink to a different bin count
is rejected rather than silently rebuilt. The index stores record names without
a prefix, so pass `--target-prefix` to `run`, not to `index`. `hspZ index`
refuses record names that are empty or contain whitespace, and bins over
4,294,967,295 bp, before it builds anything. `--index` belongs to `run`;
`benchmark` and `--cpu-only` reject it.

## Choosing `-B`

The default 500 Mbp preserves the KegAlign-matched digest; hspZ never changes it
merely because `--gpus` changed. It is also the measured multi-GPU default: the
unit partition balances the default layout's work units across the workers
(−11.9% on 2× RTX 4090, −5.1% on 4×), while coarser layouts, down to one
reference bin per worker, measured 17–22% slower than the default on a 2× T4
screen.

Any other `-B` or `--query-block-size` is a different frozen plan with its own
digest. To look for a faster layout on a specific machine, `-B 0` prints and
runs an automatic count-balanced layout; measure it against the default on that
machine before adopting it. With one worker (the smaller of `--gpus` and the
visible GPUs) it is exactly the default plan. With W ≥ 2 the reference takes the
smallest multiple of W bins that is not coarser than the default layout (at most
one bin per record), and the query becomes one bin when it fits both the
per-worker device budget and host memory (an explicit `--query-block-size` is
honoured); a candidate that does not fit falls back to the default policy, or
fails when `--query-block-size` was given. The `layout: auto W=…` line prints
the `--seq-block-size` and `--query-block-size` that reproduce the plan, and
`--dump-manifest` records them. `-B 0` cannot be combined with
`--kegalign-bins`, `--query-list` or `--index`; `HSPZ_LAYOUT_FORCE_WORKERS=W`
resolves the W-worker layout on a machine with fewer GPUs. Use
`--query-block-size` to avoid splitting the query merely because the reference
needs more bins.

Before spending GPU time on a layout, `hspZ hits-estimate` (CPU only) prints one
row per work unit: reference bin, query bin, their sizes in bp and the exact
number of seed hits the unit will expand. It plans like `run` with the same
flags, as long as `run` does not shrink the plan to fit the device (`-B 0`
resolves to the default layout, as `run` does on one GPU; to preview an automatic
layout, pass the `--seq-block-size` and `--query-block-size` its `layout:` line
printed), and its counts equal the `hits` column of the `--time` unit ledger; GPU time per unit
tracks that count (about 0.37 ns per hit on an RTX 4090, 0.54 on an A100 80GB PCIe). `--stride N`
counts every N-th query window and scales by N, an approximation. `run` never calls it; to weigh a
multi-GPU split by these exact counts, pass the table to `run` as `HSPZ_UNIT_COST=hits:PATH`.
