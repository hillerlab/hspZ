## Worker model

`--gpus W` creates up to W workers. When each worker has its own device and
every device the run uses is the same class (equal SM count and L2, nominal
clocks within 10%), the frozen plan's work units are split across the workers
by count quotas: whole reference bins first, then contiguous query slices of as
few bins as possible, at the price of one extra reference build per split bin.
Otherwise each worker owns complete reference bins, assigned by deterministic
longest-processing-time scheduling, and runs every query bin against them.
`HSPZ_UNIT_PARTITION=0|1` forces either policy (see the knobs below). Workers
beyond the number of reference bins stay idle; more workers than devices
time-slice a device and are a correctness configuration, not a speed
configuration.

GPU completion order never controls output order. Each result carries its
`WorkUnit.ordinal`, and the emitter replays those ordinals in the planned order.

## Seeder policy

| workers | default query seeder |
| ---: | --- |
| 1 | CPU, with pinned asynchronous upload when supported |
| more than 1 | device |

For controlled measurements only:

```bash
HSPZ_DEVICE_SEEDS=0 hspZ run ...  # force CPU
HSPZ_DEVICE_SEEDS=1 hspZ run ...  # force device
```

## Runtime tuning knobs (0.0.4)

Every knob is exact: every mode produces the same HSP set and the same bytes.

| variable | default | what it does |
| --- | --- | --- |
| `HSPZ_REF_BUCKETS=auto\|1\|0` | `auto` | Reference-locality bucketing before the score gate. It wins where lower DRAM traffic lets a power-capped GPU raise its clock (L4: −6.5% whole-genome wall) and loses where the card already runs near its boost clock (RTX 4090: +3.7%). `auto` measures both paths per engine in blocks of ≥3 s, discards each block's first second, and commits to the faster one after six blocks — about 20 s of gate time per engine. Shorter engines, for example 5 Mbp queries run as separate processes, stay on the off path, so set `HSPZ_REF_BUCKETS=1` on L4-class cards for those. `--time` prints the blocks and the decision. Cards whose L2 cannot hold the smallest window (T4) stay off. |
| `HSPZ_REF_BUCKET_SHIFT=<16..31>` | derived from L2 | Pins the bucket window size (implies on). |
| `HSPZ_CHUNK_WALK=full` | sparse | Restores the pre-0.0.4 chunk walk that copied the whole cumulative hit array per seed batch (rollback only). |
| `HSPZ_UNIT_PARTITION=auto\|0\|1` | `auto` | Splits the frozen plan's work units across workers by count quotas when every device the run uses is the same class and each worker has its own device (W=1, time-sliced workers and mixed classes keep whole-bin ownership); output is unchanged. −11.9% seed-and-filter wall on 2× RTX 4090 (1,400 → 1,233 s) and −5.1% on 4× RTX 4090 (718 → 681 s) at `MAX_HITS=16,711,680`. Other worker counts and device classes are unmeasured; compare with `HSPZ_UNIT_PARTITION=0`. |

## Many queries against one reference

`--query-list` runs every listed query FASTA in one process:

```bash
hspZ run \
  --reference ref.2bit \
  --query-list queries.txt \
  --output OUT \
  --gpus 1
```

`queries.txt` holds one query path per line (blank lines and `#` comments are
ignored). Each reference bin is built and uploaded once instead of once per
query, while every query keeps its own plan, cap, seed batches, dedup scopes
and `-D` history, so its output under `OUT/000001/`, `OUT/000002/`, … is
byte-identical to a standalone run. `-Z` writes one archive per job;
`OUT/queries.tsv` maps job → path, size, sha256, blocks, units, HSPs and
completion. A failing job aborts the batch (partial outputs may remain).

With `--gpus W` above one, the whole batch's work units are spread over the
workers by the same count partition a single query uses (`HSPZ_UNIT_PARTITION`
still decides the policy), and the receiver reorders each job's results, so the
per-job output is unchanged. On two RTX 4090s, 100 queries of 5 Mbp against hg38
finish in 255 s at `--gpus 2` against 497 s at `--gpus 1`; on one L4 the same
list takes 1,890–1,900 s batched against 10,400–11,600 s as separate runs. Both
arms of each comparison ran the same pinned settings (device seeder; bucketing on
for the L4, off for the RTX 4090s; the partition forced at `--gpus 2`), not the
`--gpus 1` defaults. Whole-chromosome queries gained about 3%; whole-genome
queries are expected to gain under 1% (reference setup is 0.27% of a whole-genome
run; not measured in batch mode). The saving is the reference preparation, which
by the cost model dominates only below roughly 130 Mbp of query per run on a 4090
(30 Mbp on an L4).

All jobs must plan to identical reference bins; `-B 0`, `--kegalign-bins` and
`--from-manifest` are rejected in batch mode. Bin-major order delays the first
result: check `OUT/queries.tsv` rather than waiting on the first job directory.

## Reusing a reference across runs

When queries arrive in separate runs, build the reference's tables once:

```bash
hspZ index --reference ref.2bit --index /local/ref.hspz-index
hspZ run --reference ref.2bit --query q.fa --index /local/ref.hspz-index --output OUT
```

`hspZ index` writes each reference bin's seed tables and encoded bases as raw
arrays with a text manifest, published atomically once a `READY` marker is
written. A run given `--index` loads them instead of rebuilding, inside the same
prefetch, and its output is byte-identical to a run without the index. Before
anything reaches the GPU the run proves the index matches: the parsed reference
records must hash to the value recorded at index time (an edit of the same size
is caught), the resolved plan must have exactly the index's bins, and every array
must match its recorded length and checksum.

hg38 at the default layout takes about 120 s to index and 8.9 GB on disk, and
each run then loads its seven bins in roughly 12 s. On an L4 all but the first
load (about 1.7 s) hide behind the GPU; on faster cards a small query's GPU time
per bin (about 0.6 s for 5 Mbp on an RTX 4090) is shorter than a bin load (about
1.8 s), so the loads set the pace. Each run also re-reads the reference and
re-hashes it to prove the index matches (about 4–5 s for hg38). On an L4, with
bucketing pinned on, the device seeder and the index on local NVMe with a warm
page cache, 100 queries of 5 Mbp run as separate processes fall from 10,800 s to
2,680 s.
Keep the index on local storage: a bin load above 10 s warns, and on a slow
network file system loading can cost more than rebuilding. `-B 0` is rejected by
both commands, and a plan the device budget would shrink to a different bin count
is rejected rather than silently rebuilt.

## Choosing `-B`

The default 500 Mbp preserves the KegAlign-matched digest; hspZ never changes it
merely because `--gpus` changed. It is also the measured multi-GPU default: the
unit partition balances the default layout's work units across the workers
(−11.9% on 2× RTX 4090, −5.1% on 4×), while coarser layouts, down to one
reference bin per worker, measured 17–22% slower than the default on a 2× T4
screen.

Any other `-B` or `--query-block-size` is a different frozen plan with its own
digest. To look for a faster layout on a specific machine, `-B 0` prints and
runs an automatic count-balanced layout; measure it against the default on that
machine before adopting it. Use `--query-block-size` to avoid splitting the
query merely because the reference needs more bins.
